The Azure Blob Storage connector enables the import of voice recordings, pre-transcribed voice conversations, chat transcripts, and associated CSV metadata from Microsoft Azure Blob Storage into Quality AI Express.

It automatically retrieves new files on a configurable schedule, making conversations available for supported quality evaluations and analytics. The connector supports both voice and chat interactions from third-party CCaaS platforms.

## How Connectors Work

Connectors integrate Quality AI Express with external systems where customer conversations are stored, such as cloud storage and telephony platforms. Once configured and enabled, they automatically transfer conversations into Quality AI Express for evaluation and analysis, eliminating the need for manual file uploads.

## Connector Overview and Management

Connectors link Quality AI Express to external systems and storage locations that contain conversation data. After a connector is configured, tested, and enabled, it retrieves conversation files on its configured schedule and makes successfully processed conversations available for supported quality evaluations and analytics. Manual uploads are not required for files retrieved by this connector.

The Connectors page lists the configured conversation sources. Each row represents one connector.

### Who Can Use This Page

You need the **Auto QA** permission with Full access to view and manage connectors. Contact your administrator if the page is unavailable or connector changes are blocked. Your deployment may expose the page under **Quality AI** > **Configure** > **Connectors** or under the Integrations and Extensions area.

### Connector list
| Column | Description |
| --- | --- |
| **Connector Name** | Name assigned during setup. Select the name to open the connector configuration. |
| **Created By** | User who created the connector. |
| **Modified By** | User who last changed its configuration. |
| **Channel** | Conversation channel handled by the connector: Chat, Voice, or Chat and Voice. |
| **Last Sync** | Date and time of the most recent sync, together with its configured frequency. This is blank before the first run. |
| **Status** | Indicates whether the connector is enabled or paused. |
| **Actions** | Provides the available edit, delete, and log-history actions. |

When no connectors are configured, the page displays an empty state. Select **+ New Connector** or **+ Add Connector** to create one. A loading message may appear while the connector list is being retrieved. The available connector types depend on your deployment. This guide covers **Azure Blob Storage**.

### Connector Setup Tabs

To add this source, select **+ New Connector** or **+ Add Connector**, choose **Azure Blob Storage**, and complete the setup panel. The panel is organised into the following tabs or sections. Labels and availability can vary by deployment.

| Tab | Purpose |
| --- | --- |
| **Instructions** | Provides setup guidance and links to connector-specific documentation. Review this tab before entering credentials or paths. |
| **Configuration** | Selects Azure Blob Storage, sets the connector name and region, chooses the channel and path arrangement, and captures authentication details. |
| **Schedule** | Defines how frequently the connector checks Azure Blob Storage and the earliest date from which conversations are retrieved. |
| **Test** | 	Runs connection, path, file-format, and metadata checks before the connector is saved and enabled. Correct any reported issues and run the test again before relying on scheduled ingestion. |


### Enable or Disable a Connector

Use the **Status** toggle to pause or resume a connector.
- **Disable**: Confirm the prompt to pause syncing. No new conversations are retrieved while the connector is disabled. Conversations already ingested remain in Quality AI Express.
- **Enable**: Turn the toggle on to resume the connector's configured schedule. A separate confirmation may not be displayed.

### Edit a Connector

Select the edit action for the connector to reopen its setup panel. Review and update the available configuration, authentication, storage paths, channel settings, queue mappings, or schedule, then save the changes. Re-run the connection test after changing credentials or paths.

### View Connector Logs

Open the connector's log history to review previous sync runs. Depending on the deployment, the log view can include:
- Run start and finish times.
- Number of files uploaded or retrieved and number processed.
- Number of conversations retrieved during the sync run.
- Job status and processing errors.
- A details view for an individual ingestion job.

Use the logs to confirm that a schedule ran and to investigate missing or rejected conversations.

### Delete a Connector

Select the delete action and confirm the prompt. Deleting a connector permanently removes its configuration and stops future syncing. Conversations already ingested aren't deleted. This action can't be undone.

### Service Principal Permissions

Service Principal authentication requires the following Azure role assignment.

| Role | Scope | Purpose |
|---|---|---|
| **Storage Blob Data Reader** | Storage Account | Read and list blobs. |

Assign the Storage Blob Data Reader role to the service principal associated with your App Registration. Assign the role at the storage account scope to provide the required permissions to list and read blobs.

The role assignment must target the correct service principal identity, not an unrelated user or application.

Navigate to: **Storage Account** > **Access Control (IAM)** > **Add role assignment**.

Avoid assigning broader permissions such as Contributor or Owner.

## Authentication Methods

The Azure Blob Storage connector supports two authentication methods:

- **Service Principal (Recommended)**: Uses Microsoft Entra ID application credentials to authenticate with Azure Blob Storage. This method supports connections from AWS, GCP, Oracle Cloud, and other environments without requiring Azure-hosted infrastructure.

- **Connection String**: Uses an Azure Storage Account connection string containing the account access key.

The available configuration fields depend on the selected authentication method.

### Service Principal (Recommended)

Service Principal provides identity-based authentication using an Azure App Registration.

The following credentials are required:

- Tenant ID
- Client ID
- Client Secret
- Storage Account Name

The App Registration must have the `Storage Blob Data Reader` role assigned to the storage account.

### Connection String

The connector authenticates with Azure Blob Storage using a connection string.

To obtain the connection string:

1. Open the Azure portal.
1. Navigate to **Storage Account**.
1. Select the required storage account.
1. Go to **Security + Networking** > **Access Keys**.
1. Copy the **Connection String** for **Key1** or **Key2**.
1. Use the connection string while configuring the connector.

Example format:

`DefaultEndpointsProtocol=https;AccountName=...;AccountKey=...;EndpointSuffix=core.windows.net`

<Note> The fields displayed in the connector vary depending on the selected **Auth Type**. </Note>

## Supported Data Types

The connector supports stereo voice, mono voice, voice transcripts, and chat transcripts.

| Data Type            | Format   | Files per Conversation | Analytics                               | Channel Assignment                                                                |
| -------------------- | -------- | ---------------------- | --------------------------------------- | -------------------------------------------------------------------- |
| **Stereo Voice**     | WAV, MP3 | 1                      | Complete Analytics, Enhanced Analytics  | Single dual-channel recording (Left = Agent, Right = Customer).                    |
| **Mono Voice**       | WAV, MP3 | 2                      | Complete Analytics, Enhanced Analytics  | Separate agent and customer recordings. Mixed audio isn't supported. |
| **Voice Transcript** | JSON     | 1                      | Text Analytics, Complete Text Analytics | Pre-transcribed voice conversation.                                  |
| **Chat Transcript**  | JSON     | 1                      | Text Analytics, Complete Text Analytics | Message-level chat transcript.                                       |

### Stereo Voice

A stereo recording contains both agent and customer audio in a single dual-channel recording.

- **Left channel**: Agent.
- **Right channel**: Customer.
- One audio file per conversation.

Channel assignments must be represented correctly in the CSV metadata using `agentChannel` and `customerChannel`.

### Mono Voice
Mono conversations require two separate audio files:

- **Agent recording**
- **Customer recording**

Example:

- `conv-123456-agent.wav`
- `conv-123456-customer.wav`

A single mixed mono recording isn't supported.

Each mono conversation must have two CSV rows sharing the same `conversationId`.

### Voice Transcripts

Voice transcripts allow importing previously transcribed voice conversations without reprocessing the original audio.

- Format: JSON.
- One transcript file per conversation.
- `recordingType = transcription`.
- `channelType = voice`.

### Chat Transcripts

Chat transcripts support conversations from platforms such as:

- Web Chat, WhatsApp, Facebook Messenger, and other supported messaging platforms.
- Format: JSON.
- One transcript file per conversation.
- `recordingType = transcription`.
- `channelType = chat`.

## Data Flow

The Azure Blob Storage connector imports conversation recordings, transcripts, and metadata into Quality AI Express through the following process:

1. **Azure Blob Storage:** Stores audio recordings, voice transcripts, chat transcripts, and CSV metadata files.
2. **Connector Authentication:** The connector authenticates with Azure Blob Storage using the configured Service Principal or Connection String.
3. **Data Ingestion:** The connector accesses the configured Blob container and retrieves the metadata and associated conversation files.
4. **Conversation Processing:** Quality AI Express processes the ingested conversations. Audio recordings are transcribed and analyzed, while existing transcripts are processed as text.
5. **Analytics:** Processed conversations become available in Quality AI Express dashboards for quality evaluation, sentiment analysis, topic identification, and other supported analytics.

## CSV Metadata Formats

This section defines the required CSV metadata fields for each supported conversation type.

Core fields are shared across conversation types, while recording-specific fields differ.

### Azure Blob File and Metadata Checklist

Before running ingestion, verify that:

- Each configured ingestion folder contains the required `test.csv` file and the metadata CSV uses the required headers.
- Conversation start and end timestamps use ISO 8601 UTC format (`YYYY-MM-DDTHH:MM:SSZ`), and the end time is later than the start time.
- Each queueId maps to an existing Quality AI Express queue.
- Every audio or transcript path referenced by the metadata exists in the configured Blob container and is accessible to the connector.
- Files use a supported format (WAV, MP3, JSON, or CSV, as applicable) and don't exceed the documented 50 MB per-file limit.

The detailed schemas below are Azure-specific. Don't assume that a field or file format documented for another connector is supported by `Azure Blob Storage`.

### Common Metadata Requirements

The following requirements apply when preparing metadata CSV files:

- Conversation start and end timestamps must use ISO 8601 UTC format.
- The conversation end time must be later than the conversation start time.
- The `agentEmail` must match a valid platform user account.
- The `queueId` must match an existing Quality AI Express queue mapping.
- The `conversationId` must not exceed 50 characters.
- Language defaults to `en` when the optional language field is omitted.

For mono recordings, both CSV rows must share the same `conversationId` and reference the corresponding agent and customer recordings.

### CSV Metadata File: Required Columns

Each configured ingestion path must contain a CSV metadata file. The CSV identifies each conversation and references the audio or transcript content that Quality AI Express must retrieve.

| Column | Type | Required | Description |
| --- | --- | --- | --- |
| `conversationId` | String | Yes | Unique identifier for the conversation. The generic connector also accepts `clientConversationId`. The Azure guide additionally limits this value to 50 characters. |
| `conversationStartTime` | Date/time | Yes | Conversation start time. Use the Azure guide's ISO 8601 format, such as `2025-04-10T14:30:00Z`. |
| `conversationEndTime` | Date/time | Yes | Conversation end time. It must be later than the start time. |
| `queueId` | String | Yes | Queue identifier matching a configured Quality AI Express queue mapping. Use the queue's custom ID. |
| `queueName` | String | Yes | Queue name; supported by the generic connector when `queueId` is not supplied. At least one of `queueId` or `queueName` is required by the generic connector. Confirm whether `queueName` is accepted by the Azure connector version in your deployment. |
| Content reference | URL or path | Yes | Supply the content reference appropriate to the conversation: `recordingU

For Azure Blob ingestion, use the field names and path conventions shown in the Azure-specific tables in this guide. The generic connector schema also documents `callId` as an alternative content reference for integrations that retrieve audio through a separate call-system integration. Don't assume that `callId` is supported by this Azure Blob connector unless it's enabled in your deployment.

### CSV Metadata File: Optional Columns

The generic connector supports the following optional metadata. Availability can depend on the Azure connector version and the Quality AI Express configuration.

| Column | Type | Default | Description |
| --- | --- | --- | --- |
| `agentEmail` | String | — | Email address of the agent who handled the conversation. It must match an active Quality AI user and, where required, the queue assignment. |
| `channelType` | String | Auto-detected | `voice` or `chat`. If omitted in the generic connector, `chatScriptUrl` indicates chat; otherwise the channel is treated as voice. |
| `recordingType` | String | Auto-detected | `stereo`, `mono`, or `transcription`, based on the content reference fields. |
| `contactDirection` | String | `Inbound` | `Inbound` or `Outbound`. |
| `language` | String | `en` | Language code, such as `en`, `es`, or `fr`. It must be enabled in the QM language settings. |
| `asrProvider` | String | `microsoft` | Speech-to-text provider used for voice files. |
| `agentChannel` | Number | `1` | Agent audio channel in a stereo file. Must be `0` or `1` and differ from `customerChannel`. |
| `customerChannel` | Number | `0` | Customer audio channel in a stereo file. Must be `0` or `1` and differ from `agentChannel`. |
| `agentSpeakerId` | Number | `2` | Agent speaker ID when diarization is enabled. Must differ from `customerSpeakerId`. |
| `customerSpeakerId` | Number | `1` | Customer speaker ID when diarization is enabled. Must differ from `agentSpeakerId`. |
| `isSpeakerEnabled` | Boolean | `false` | Set to `true` to route transcript speakers by speaker ID instead of audio channel. |
| `callId` | String | — | Third-party call identifier. Use only when the corresponding integration is configured. |

### Accepted Date Formats

The generic connector accepts date values that JavaScript's Date constructor can parse. The documented formats include:

| Format | Example |
| --- | --- |
| ISO 8601 | `2024-01-15T10:30:00Z` |
| ISO 8601 with milliseconds | `2024-01-15T10:30:00.000Z` |
| Epoch milliseconds as a number | `1705316400000` |
| Epoch milliseconds as a string | `"1705316400000"` |

For Azure Blob connector setup, follow the stricter Azure-specific prerequisite in this guide and provide ISO 8601 timestamps (`YYYY-MM-DDTHH:MM:SSZ`). Avoid locale-specific date formats such as `01/15/2024`, which can be interpreted differently by different environments.

### How Conversation Type is Determined

The generic connector can infer the channel and recording type from content-reference fields when `channelType` and `recordingType` aren't explicitly supplied. For `Azure Blob Storage`, use the explicit Azure-specific field names and combinations in the data-type tables below. Don't rely on generic inference unless your deployed connector version documents it.

| Content reference present | Channel type | Recording type | Processing |
| --- | --- | --- | --- |
| `chatScriptUrl` | `chat` | `chat` | Reads the chat transcript directly and sends it for text evaluation. |
| `transcriptUrl` without audio | `voice` | `transcription` | Reads the pre-transcribed voice content and skips audio transcription. |
| `agentRecordings` and `customerRecordings` | `voice` | `mono` | Processes the separate agent and customer audio tracks. |
| `recordingUrl` only | `voice` | `stereo` | Splits the stereo recording by the configured channel assignments and transcribes it. |


If `channelType` and `recordingType` are explicitly provided, the generic connector uses those values instead of detecting them. Confirm the Azure-specific field names and supported combinations in the data-type tables above before preparing production files.

| Agent Onboarded | Queue Onboarded | Processing Result |
|----------------|----------------|------------------|
| No | Yes | Conversation is processed. |
| Yes | Yes | Conversation is processed, even if the agent isn't mapped to the queue. |

## JSON Transcript Schemas

Detailed JSON transcript structure and mandatory fields.

### Voice Transcript

The root JSON object contains a `recognizedPhrases` array.

Each phrase can include:

- `recognitionStatus`
- `channel`
- `offset`
- `duration`
- `offsetInTicks`
- `durationInTicks`
- `durationMilliseconds`
- `offsetMilliseconds`
- `nBest`
- `words`

Each `nBest` alternative can include:

- `confidence`
- `lexical`
- `itn`
- `maskedITN`
- `display`
- `words`

Each word can include:

- `word`
- `offset`
- `duration`
- `offsetInTicks`
- `durationInTicks`
- `durationMilliseconds`
- `offsetMilliseconds`
- `confidence`
- `Required fields`

| JSON Level | Required Fields |
|------------|----------------|
| `Phrase` | `channel`, `offsetInTicks`, `nBest` |
| `nBest` | `lexical`, `words` |
| `Words` | `word`, `offsetInTicks`, `durationInTicks`, `confidence` |

### Chat Transcript

The root JSON object contains messages identified by numeric keys (for example, 1, 2, 3).

Each message requires the following fields:

| Field | Values | Description |
|-------|--------|-------------|
| `type` | `AGENT`, `USER`, `SYSTEM` | Identifies the speaker. |
| `text` | String | Message content. |
| `timestamp` | Unix time in milliseconds | Message timestamp. |
| `userId` | String | Agent email or customer ID. |

### Chat Transcript File: `chatScriptUrl` format

For the generic connector, `chatScriptUrl` is used for chat conversations, not voice recordings. The JSON file must be a flat JSON object (not an array and not wrapped in a parent `conversation` property). Each key is a numeric message index and each value is a message object.

Two timestamp formats are supported by the generic connector. The selected format is controlled by the conversation source configuration setting `chatscriptTimestampFormat`.

### Offset Format (Default)

Each message contains `offset`, the number of milliseconds from `conversationStartTime`.
{
  "1": { "type": "AGENT", "text": "Hello, how can I help?", "offset": 0 },
  "2": { "type": "USER", "text": "I have a billing question.", "offset": 10000 },
  "3": { "type": "AGENT", "text": "Let me check that for you.", "offset": 15000 }
}

`conversationStartTime` is required. The message time is calculated as the conversation start time plus the offset.

### Unix Timestamp Format

Each message contains timestamp, a Unix epoch value in milliseconds (not seconds).
{
  "1": { "type": "AGENT", "text": "Hello, how can I help?", "timestamp": 1705316400000 },
  "2": { "type": "USER", "text": "I have a billing question.", "timestamp": 1705316410000 },
  "3": { "type": "AGENT", "text": "Let me check that for you.", "timestamp": 1705316415000 }
}

The first message timestamp must be at or after `conversationStartTime`. The last message timestamp must be at or before `conversationEndTime`.

### Chat Message Field Rules

| Field | Required | Allowed values or format |
|---|---|---|
| Message key | Yes | Numeric string, such as `0`, `1`, or `2`. The sequence must start at `0` or `1`. |
| `type` | Yes | Generic connector: `AGENT`, `USER`, `BOT`, or `CUSTOMER` (case-insensitive). The Azure-specific schema in this guide also documents `SYSTEM`; verify accepted values for the deployed Azure connector version. |
| `text` | Yes | Message content as a string. |
| `offset` | Yes, for offset format | Non-negative milliseconds from conversation start. |
| `timestamp` | Yes, for Unix format | Non-negative Unix epoch timestamp in milliseconds, within the conversation start/end range. |
| `userId` | Azure-specific | Agent email or customer identifier, where required by the Azure transcript schema. |

Don't mix `offset` and `timestamp` formats within a transcript. Use the timestamp format configured for the conversation source.

### Pre-Transcribed Voice Transcript File: `transcriptUrl`

The generic connector accepts a pre-transcribed voice file in Microsoft Azure Cognitive Services batch transcription format. The root JSON object contains a `recognizedPhrases` array. This lets the connector process an existing transcript without sending the original audio through its own ASR workflow.

A phrase contains timing information, a channel or speaker identifier, and an `nBest` array. The first alternative (`nBest[0]`) is used.

json
```
{
  "recognizedPhrases": [
    {
      "offsetInTicks": 10000000,
      "durationInTicks": 25000000,
      "channel": 1,
      "nBest": [
        {
          "lexical": "hello how can i help you today",
          "confidence": 0.95,
          "words": [
            {
              "word": "hello",
              "offsetInTicks": 10000000,
              "durationInTicks": 3000000,
              "confidence": 0.98
            }
          ]
        }
      ]
    }
  ]
}
```

| JSON field | Required | Description |
|---|---|---|
| `recognizedPhrases` | Yes | Top-level array. Each entry represents a spoken phrase. |
| `offsetInTicks` | Yes | Phrase start time in 100-nanosecond ticks. Divide by 10,000 to convert to milliseconds. |
| `durationInTicks` | Yes | Phrase duration in 100-nanosecond ticks. |
| `channel` | Yes, channel-routing mode | Audio channel number. It must match the configured agent or customer channel. |
| `speaker` | Yes, diarization mode | Speaker ID used when `isSpeakerEnabled = true`; it replaces channel-based routing. |
| `nBest` | Yes | Recognition alternatives. The system uses `nBest[0]`. |
| `nBest[0].lexical` | Yes | Recognised phrase text. Empty lexical values are skipped. |
| `nBest[0].confidence` | No | Confidence score from 0 to 1. |
| `nBest[0].words` | No in generic schema; required by the Azure-specific schema above | Word-level text, timing, and confidence values. |

All `offsetInTicks` and `durationInTicks` values use 100-nanosecond ticks. For example, 10,000,000 ticks equals 1,000 milliseconds (one second).

## Prepare Service Principal Authentication

Complete the Azure App Registration and Service Principal configuration before setting up the connector.

Skip this section if you are using Connection String authentication. 

Service Principal authentication requires the following four credentials:

| Credential | Azure Source | Purpose |
|---|---|---|
| `accountName` | Azure Storage Account overview | Identifies the Azure Storage Account. |
| `tenantId` | App Registration overview | Identifies the Microsoft Entra ID tenant. |
| `clientId` | App Registration overview | Identifies the registered application. |
| `clientSecret` | Certificates & secrets | Authenticates the application. |

You must also assign the `Storage Blob Data Reader` role to the service principal associated with your App Registration.

<Note> Use the Client Secret **Value**, not the Secret ID, when configuring the connector. </Note>

**Step 1: Create an App Registration**

1. Go to the [Azure Portal](https://portal.azure.com/).
2. Search for **Microsoft Entra ID** (formerly Azure Active Directory).
3. Select **App registrations**.
4. Select **+ New registration**.
5. Enter a name for the application and configure the registration as required.
6. Select **Register**.

After registering the application, open the App Registration overview page and copy the following values:

| Credential | Where to Find It |
|---|---|
| **Application (client) ID** | Available under Essentials on the App Registration overview page. |
| **Directory (tenant) ID** | Available under Essentials on the App Registration overview page. |

Save both values securely. You may need them when configuring the connector.

You can find the **Storage Account Name** by opening the required Azure Storage Account and checking its overview page. Use this value as the `accountName` credential when configuring the connector.

<Note> The Client Secret is created in the next step. When configuring the connector, use the Client Secret **Value**, not the Secret ID. </Note>


### Client Secret Expiration

When creating the client secret:

- Enter a descriptive name, such as `quality-ai-key`.
- Select an appropriate expiration period. The original setup recommendation is at least 12 months.
- Copy the Client Secret Value immediately after creation.
- Store the secret securely.

The Client Secret Value is displayed only once. If you lose it, create a replacement secret and update the connector configuration.

**Step 2: Create a Client Secret**

A client secret acts as the password that the App Registration uses to prove its identity.

1. Open the App Registration you created.
1. Select **Certificates & secrets** from the left navigation menu.
1. Select the **Client secrets** tab.
1. Select **+ New client secret**.
1. Enter a description, such as quality-ai-key.
1. Select an expiration period of at least 12 months.
1. Select **Add**.

The newly created secret appears in the table.

| Column | Action |
|---|---|
| **Value** | Copy this value. It's the Client Secret required by the connector. |
| **Secret ID** | Don't use this value. It's an internal identifier, not an authentication credential. |

<Note>The Client Secret Value is visible only once. Copy it immediately and store it securely. If you navigate away without saving it, you must delete and recreate the secret. Don't use the Secret ID in the connector configuration.</Note>

**Step 3: Grant the App Registration Access to the Storage Account**

The App Registration doesn't have access to Azure Blob Storage by default. Assign the required role at the storage account level.

1. Open the Azure portal.
1. Search for **Storage accounts**.
1. Open the required storage account.
1. Select **Access Control (IAM)** from the left navigation menu.
1. Select **+ Add** > **Add role assignment**.
1. Under the Role tab:
    - Search for `Storage Blob Data Reader`.
    - Select the role.
    - Select **Next**.
1. Under the Members tab:
    - Set **Assign access to** to **User**, **group**, or **service principal**.
    - Select **+ Select members**.
    - Search for the App Registration name, such as quality-ai-connector.
    - Select the App Registration.
    - Select **Select**.
    - Select **Review + assign**.
    - Select **Review + assign** again to confirm.

The role assignment appears under **Access Control (IAM)** > **Role assignments**.

<Note>Role assignments can take up to 10 minutes to propagate. Wait for the permissions to become effective before testing the connector.</Note>

**Minimum required permission**: `Storage Blob Data Reader` at the storage account scope is sufficient. Don't assign broader roles such as Contributor or Owner.

**Step 4: Configure the Storage Account Firewall (If Required)**

If the Azure Storage account has network access restrictions enabled, the Quality AI service may be blocked even when the authentication credentials and role assignments are correct. In this case, add the outbound IP address provided by your Kore.ai administrator to the storage account firewall allowlist.

1. Open the required storage account in the Azure portal.
1. Select **Networking** under **Security + networking**.
1. Under **Firewalls and virtual networks**, check the network access configuration.
1. If **Enabled from selected virtual networks and IP addresses** is selected:
    - Locate the **Firewall** section.
    - Enter the outbound IP address provided by your Kore.ai administrator in the **Address range** field.
1. Select **Save**.

<Note> To determine whether this step is required, navigate to **Networking** > **Public network access**. If the storage account is configured to allow access only from selected virtual networks and IP addresses, the firewall must allow the Quality AI service's outbound IP.</Note>

Before you begin, verify that your Blob container is ready:

- Upload all required files to Azure Blob Storage.
- Metadata `.csv` files contain required fields and valid values.
- Mono conversations have separate agent and customer files.
- The container and folder paths are available.
- A `test.csv` file exists in each ingestion path.
- Blob permissions enable the connector to access the files.

<Note> File and folder names shouldn't contain any spaces or special characters.</Note>

### Step 1: Create the Connector

1. Navigate to **Quality AI** > **Configure** > **Connectors**.
2. Select **+ Add Connector** > **Azure Blob Storage** > **Connect**.
3. Enter a **Name** for the connector.
4. Select the **Azure Region** where your storage account is located. For example, `eastus` identifies the East US region.
5. Select the required **Authentication Type**.

**Connector Name Validation**

Enter a unique name for the connector. Connector names must not duplicate existing connector names. If you enter a name that is already in use, an error appears when you try to save the connector.

#### Option 1: Service Principal (Recommended)

Select **Service Principal** as the Authentication Type.

Enter the following credentials:

| Field | Description |
|---|---|
| **Account Name** | Name of the Azure Storage Account. |
| **Tenant ID** | Directory (tenant) ID from the Microsoft Entra ID App Registration overview. |
| **Client ID** | Application (client) ID from the App Registration overview. |

<Note> Make sure that the App Registration's service principal has the `Storage Blob Data Reader` role assigned to the Azure Storage Account.</Note>

`DefaultEndpointsProtocol=https;AccountName=...;AccountKey=...;EndpointSuffix=core.windows.net`

   - **Unified Path**: Enter a single Blob path for both voice and chat data.

## Troubleshooting

### Authentication Issues

| Problem | Symptom | Resolution |
|---|---|---|
| **AuthorizationFailure** | Access is denied despite valid credentials. | Check the storage account firewall configuration. If network restrictions are enabled, add the Quality AI service outbound IP provided by your administrator to the allowlist. |
| **Invalid Client Secret** | Microsoft Entra ID authentication fails because the client secret is invalid. | Verify that the Client Secret Value is correct and hasn't expired. Generate a new secret if necessary. Don't use the Secret ID. | **Invalid Tenant ID** | Service Principal authentication fails because the tenant can't be identified. | Verify the Directory (tenant) ID from the Microsoft Entra ID App Registration overview. |
| **Invalid Client ID** | Azure can't identify the registered application. | Verify the Application (client) ID from the App Registration overview. |
| **Invalid Account Name** | The connector can't identify or access the configured storage account. | Verify that the Account Name matches the Azure Storage Account name. |
| **Expired Client Secret** | Service Principal authentication fails after the client secret expires. | Generate a new Client Secret Value and update the connector configuration. |
| **AuthorizationPermissionMismatch** | The connector can't read or list Blob files. | Verify that `Storage Blob Data Reader` is assigned to the correct service principal at the storage account scope. Allow up to 10 minutes for role assignments to propagate. |
| **Azure connection string is required** | The connector reports a missing connection string when Connection String authentication is selected. | Verify that **Connection String** is selected as the Authentication Type. Enter the complete connection string from the Azure Storage Account Access Keys page. If Service Principal authentication is selected, verify that the correct authentication method and credentials are configured. |
| **Invalid Azure connection string** | Azure rejects the connection string when Connection String authentication is selected. | Copy the complete connection string directly from Azure Access Keys without modifying it. Verify that the connection string belongs to the intended storage account. |

### Storage Access Issues

| Problem | Symptom | Resolution |
|---|---|---|
| **Container Not Found** | Container or path not found. | Verify the container name and folder structure. Ensure that the configured Blob path points to the correct container and folder. |
| **File Not Available** | Blob access denied or the referenced file can't be retrieved. | Verify Blob access permissions, storage account settings, and the availability of the referenced files. |

### File Validation Issues

| Problem | Symptom | Resolution |
|---|---|---|
| **File Format Validation Error** | Unsupported or invalid file format. | Verify the CSV metadata structure, supported file formats, and required headers. |
| **Metadata Validation Error** | Missing or invalid metadata. | Verify that all required metadata fields are present and contain valid values. Check the timestamp format and required field values. |

### Data Processing Issues

| Problem | Symptom | Resolution |
|---|---|---|
| **Timestamp Validation Error** | Invalid timestamp format. | Use ISO 8601 format (`YYYY-MM-DDTHH:MM:SSZ`). |
| **Queue Mapping Error** | Queue IDs aren't mapped or don't match existing queues. | Map all queue IDs to existing Quality AI Express queues before running ingestion. |

### Performance Considerations

Processing time depends on several factors, including Automatic Speech Recognition (ASR) latency for voice recordings, conversation duration, file size, LLM processing time, AI analysis complexity, and the number of conversations being ingested.

## How Connector Sync Works

### Schedule Frequency

The connector runs at the interval configured in the Schedule tab. The generic Connectors documentation describes the following interval ranges. Treat these as general connector guidance; the schedule fields and supported ranges exposed for Azure Blob Storage can vary by deployment.

#### Supported Schedule Intervals

| Interval Type | Supported Range | Behavior |
| --- | --- | --- |
| **Minutes** | 1–59 | Runs every configured number of minutes. |
| **Hourly** | 1–23 | Runs every configured number of hours. |
| **Daily** | 1–365 | Runs every configured number of days at the configured time. |

The Schedule tab also defines the start date and, for daily schedules, the start time. Use UTC for the start time, where the Azure connector configuration requests it. The start date is the earliest date from which the connector retrieves conversations; files or conversations before that date are ignored.

Each run checks the configured Blob path for files newer than the last successful sync. The Last Sync value is updated after a run.

### How a Sync Run Works

A sync run performs the following high-level actions:

1. Connects to the configured Azure storage account using the saved authentication method.
2. Checks the configured unified path or separate voice and chat paths for new metadata and content files.
3. Reads the CSV metadata and retrieves the referenced audio or transcript files.
4. Sends the files and conversation metadata for processing.
5. Makes successfully processed conversations available in the Quality AI Express conversation and analytics experience.

After ingestion, the conversation services process the audio or transcript content and create the corresponding post-call analysis record with the conversation metadata. When a conversation is associated with a mapped queue, the configured Auto QA evaluation workflow can be triggered.

Ingested conversations then use the applicable scoring, dashboard, and audit workflows. Successfully ingested conversations are available in **Conversation Mining**, the **QM Dashboard**, and other Quality AI views that display conversation data.

### Connection Status and Failed Runs

The connector's **Status** control indicates whether syncing is enabled or paused; **Last Sync** shows the most recent sync time and configured frequency. Review the log history for the outcome of an individual run.

A failed run means that new conversations were not retrieved in that run; it does not delete conversations that were ingested previously. Use the connector logs and test results to identify and correct the issue.

#### Duplicate Protection

Confirm whether Azure identifies previously ingested files using their unique path and name.

#### Connection Status and Failed Runs

Confirm that a failed run doesn't affect previously ingested conversations and that the Status and Last Sync controls behave as described.

#### Validation Failures

The generic connector documents the following conditions as permanent CSV-row failures (not retried):

- `conversationId` is missing.
- `conversationStartTime` or `conversationEndTime` is missing or cannot be parsed.
- `queueId` or `queueName` is missing, or does not match a queue configured in QM.
- No supported content reference is provided (`recordingUrl`, `agentRecordings`, `customerRecordings`, `transcriptUrl`, `chatScriptUrl`, or an enabled `callId` integration).
- `agentEmail` is provided but the agent does not exist in Quality AI or is not assigned to the queue.
- `agentChannel` and `customerChannel` have the same value.
- `agentSpeakerId` and `customerSpeakerId` have the same value when `isSpeakerEnabled` is `true`.
- `contactDirection` is not `Inbound` or `Outbound`.
- The bot has no QM features enabled in settings.
- The conversation language is not enabled in QM language settings.

#### Chat Transcript Validation Failures

A chat transcript can fail permanently under the following conditions:

- It is not a valid flat JSON object.
- A message is missing its speaker, text, or configured time field.
- A speaker value is unsupported.
- A time value is negative or not numeric.
- A Unix timestamp falls outside the conversation start/end range.

For Azure Blob-specific failures, also review the file-size, file-accessibility, `test.csv`, queue-mapping, and storage-path requirements in this guide.
