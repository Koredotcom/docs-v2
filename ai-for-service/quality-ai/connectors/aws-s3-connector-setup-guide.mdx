Set up the AWS S3 connector to pull voice recordings and chat transcripts from an S3 bucket into Quality AI Express for analysis.

The AWS S3 Connector pulls conversation recordings and chat transcripts from an S3 bucket into Quality AI Express on a configurable schedule. Use this connector to analyze interactions from third-party Contact Center as a Service (CCaaS) solutions.

The connector ingests voice recordings (stereo or mono), chat transcripts, pre-transcribed voice data, and metadata `.csv` files.

## Prerequisites

### AWS Requirements

| Requirement | Details |
|---|---|
| **S3 bucket** | Created in your preferred region with an organized folder structure. |
| **IAM permissions** | Read-only access (`s3:GetObject`, `s3:ListBucket`) via access keys or IAM role. |
| **Audio files** | WAV or MP3 format, maximum 50 MB each, available via HTTPS. |

## Supported Recording Types

| Type | Format | Files per Conversation | Channel Assignment | Analytics |
|---|---|---|---|---|
| **Stereo Voice** | WAV/MP3 | 1 | Left = Agent, Right = Customer | Full Analytics |
| **Mono Voice** | WAV/MP3 | 2 (separate agent/customer files) | N/A | Enhanced Analytics |
| **Voice Transcripts** | JSON | 1 | Pre-transcribed audio | Text Analytics |
| **Chat Scripts** | JSON | 1 | Message-level attribution | Full Text Analytics |

### Mono Recording Requirement

<Note>Mono recordings require two separate audio files — one for the agent and one for the customer. A single mixed mono file is not supported and significantly reduces transcription accuracy.</Note>

| Supported | Not Supported |
|---|---|
| `conv-123456-agent.wav` (agent only) + `conv-123456-customer.wav` (customer only) | `conv-123456-mixed.wav` (both speakers combined) |

## Data Flow

The connector reads the CSV metadata first. It then uses the file references in each row to retrieve the associated audio or transcript content.


```text
[S3 Bucket]
    │
    ├── CSV metadata
    └── Referenced audio / transcript files
             │
             ▼
       [S3 Connector]
             │
             ├── Authentication and path validation
             ├── CSV metadata validation
             ├── Retrieve referenced files
             └── Route by channel and recording type
                    │
          ┌─────────┴──────────┐
          ▼                    ▼
   [Voice audio]        [Pre-transcribed voice / chat]
          │                    │
          ▼                    ▼
   [ASR transcription]  [Transcript parsing]
          │                    │
          └─────────┬──────────┘
                    ▼
           [Quality AI Express]
                    │
                    ▼
           [Analytics Dashboard]
           ├── Quality Score
           ├── Sentiment
           └── Topics
```
Stereo and mono audio recordings are sent through voice processing. Pre-transcribed voice JSON and chat JSON are imported as transcript content; they do not require the connector to transcribe the source audio.

## CSV Metadata Formats

Each recording type requires specific CSV fields. The core fields are the same across all types, only the recording-specific fields differ.

### Common CSV Metadata Requirements

The generic connector specification defines the following common metadata requirements. The AWS S3-specific tables below remain authoritative for fields explicitly marked as required by this connector.

| Column | Type | Requirement | Description |
| - | - | - | - |
| `conversationId` | String | Required | Unique conversation identifier. The generic connector also accepts `clientConversationId` as an alias; confirm that the AWS S3 connector accepts this alias before using it. |
| `conversationStartTime` | Date | Required | Conversation start time. See the accepted formats below. |
| `conversationEndTime` | Date | Required | Conversation end time; it must be later than the start time. |
| `queueId` / `queueName` | String | At least one | The generic connector accepts either `queueId` or `queueName`. The AWS S3 examples and queue-mapping workflow currently document `queueId`; confirm `queueName` support for AWS S3 before using it. |
| Content reference | URL / identifier | At least one | The generic connector accepts one or more of `recordingUrl`, `agentRecordings`, `customerRecordings`, `transcriptUrl`, `chatScriptUrl`, or `callId`. The AWS S3 format-specific tables below document the AWS fields and should be followed unless additional fields are confirmed for this connector. |

<Note> Don't assume that every generic connector alias or content-reference field is supported by the AWS S3 connector. In particular, confirm support for `clientConversationId`, `queueName`, `callId`, and `transcriptUrl` before using them in an AWS S3 metadata file.</Note>

### Accepted Date and Timestamp Formats

The generic connector documentation states that conversation date values are parsed using the JavaScript `Date` constructor. It identifies these reliable formats:

| Format | Example |
| - | - |
| ISO 8601 | `2024-01-15T10:30:00Z` |
| ISO 8601 with milliseconds | `2024-01-15T10:30:00.000Z` |
| Epoch milliseconds (number) | `1705316400000` |
| Epoch milliseconds (string) | `"1705316400000"` |

ISO 8601 timestamp is the recommended format. Avoid locale-specific dates such as `01/15/2024`, because their interpretation can vary.

The AWS S3 examples currently specify ISO 8601 UTC. Confirm epoch-millisecond support for AWS S3 before using numeric or string epoch values in its CSV files.

### Optional CSV Metadata Fields

The generic connector documentation describes these optional fields. Availability and defaults must be confirmed for the AWS S3 connector where they are not already shown in its format-specific tables.

| Column | Type | Generic default / behavior | Description |
| - | - | - | - |
| `agentEmail` | String | Not required by the generic schema | Email of the agent associated with the conversation. The AWS S3 tables currently mark it as required; follow the AWS-specific requirement unless Engineering confirms otherwise. |
| `channelType` | String | Auto-detected | `voice` or `chat`. The generic connector detects chat from `chatScriptUrl`; otherwise it defaults to voice. |
| `recordingType` | String | Auto-detected | `stereo`, `mono`, or `chat` in the generic routing rules. The AWS S3 tables currently use `transcription` for pre-transcribed voice and chat; retain those AWS-specific values unless Engineering confirms a change. |
| `contactDirection` | String | `Inbound` | `Inbound` or `Outbound`. |
| `language` | String | `en` | Conversation language code. |
| `asrProvider` | String | `microsoft` | Speech-to-text provider for voice audio. The AWS S3 examples use both `asprovider` and `asProvider`. Standardize the spelling with Engineering before publishing. |
| `agentChannel` | Number | `1` | Agent channel in a stereo recording. |
| `customerChannel` | Number | `0` | Customer channel in a stereo recording. It must differ from `agentChannel`. |
| `agentSpeakerId` | Number | `2` | Agent speaker ID when speaker diarization is enabled. |
| `customerSpeakerId` | Number | `1` | Customer speaker ID when speaker diarization is enabled. It must differ from `agentSpeakerId`. |
| `isSpeakerEnabled` | Boolean | `false` | Enables speaker-based routing instead of channel-based separation for supported voice transcripts. |
| `callId` | String | No default | Third-party call identifier. The generic connector lists it as an alternative content reference. AWS S3 support needs confirmation. |

### Generic Connector Routing Reference

The generic connector documentation describes the following automatic routing behavior:

| CSV content reference | Generic `channelType` | Generic `recordingType` | Processing |
| - | - | - | - |
| `chatScriptUrl` | `chat` | `chat` | Reads the chat transcript directly, skips audio processing. |
| `agentRecordings` and `customerRecordings` | `voice` | `mono` | Processes separate agent and customer audio tracks. |
| `recordingUrl` | `voice` | `stereo` | Processes a stereo audio file using channel assignments. |

If `channelType` and `recordingType` are explicitly supplied, the generic connector documentation says those values are used directly. The AWS S3 guide currently documents `recordingType = transcription` for chat and pre-transcribed voice. Confirm the AWS-specific routing values and precedence with Engineering; do not replace the AWS values with the generic values without confirmation.

## Agent and Queue Validation

The system validates agent and queue combinations as follows:

- **Queue onboarded, agent not onboarded:**Process the conversation when the system has onboarded the queue, even if the system hasn't onboarded the agent.
- **Both agent and queue onboarded:** Process the conversation even if the agent isn't mapped to the queue.
- **Queue not onboarded or configured:** Reject the conversation.

## Chat Transcript Format

The generic connector documentation describes `chatScriptUrl` as the preferred reference for chat transcripts and `transcriptUrl` as an alternate alias.

The expected chat transcript structure is a **flat JSON object (not an array)** with numeric message keys. Each message object contains the following fields:

- `type`
- `text`
- A timestamp field

### Chat Timestamp Formats

The generic connector supports two chat timestamp formats, selected through the conversation source setting `chatscriptTimestampFormat`:

| Format | Description |
|---|---|
| `offset` | Each message uses `offset`, specified in milliseconds relative to `conversationStartTime`. |
| `unix` | Each message uses `timestamp`, specified as Unix epoch milliseconds. The first message must be at or after `conversationStartTime`, and the last message must be at or before `conversationEndTime`. |

### AWS S3 Implementation Difference to Confirm

The AWS S3 example below currently uses `timestamp` in Unix epoch milliseconds. Confirm whether the AWS S3 connector exposes or inherits `chatscriptTimestampFormat` and whether it accepts the offset format before using offset-based chat transcripts.

**Example:**

```json
{
  "1": {
    "type": "AGENT",
    "text": "Good afternoon, how can I help you today?",
    "timestamp": 1749562206000,
    "userId": "johndoe@example.com"
  },
  "2": {
    "type": "USER",
    "text": "I need help with my account balance.",
    "timestamp": 1749562253142,
    "userId": "customer_12345"
  }
}
```

**Required fields:**

| Field | Values | Notes |
|---|---|---|
| `type` | `AGENT`, `USER`, or `SYSTEM` | Identifies the speaker. |
| `text` | Message content | The message text. |
| `timestamp` | Unix timestamp in milliseconds | Message send time. |
| `userId` | Participant identifier | Agent email or customer ID. |

#### Chat Transcript Validation Checklist

The following validation rules apply to the generic connector:

- The transcript must be a JSON object, not a JSON array.
- The object must be flat; don't wrap message entries in a container property.
- Message keys must be numeric strings and begin at `0` or `1`.
- Each message must contain `type` and `text`.
- The timestamp field must match the configured timestamp mode:
  - `offset` for offset mode.
  - `timestamp` for Unix mode.
- Unix timestamps must be expressed in milliseconds, not seconds, and must fall within the conversation start and end times.

### Speaker Type Discrepancy to Verify

The generic connector field rules list `AGENT` and `USER` as the primary message type values. However:

- Another explanatory note in the generic documentation also mentions `BOT` and `CUSTOMER`.
- The AWS S3 example lists `AGENT`, `USER`, and `SYSTEM`.

Confirm the accepted speaker type values for AWS S3 with Engineering and document one consistent list. Don't assume that all speaker values supported or mentioned in the generic documentation are supported by AWS S3.

## Storage Structure Options

Choose a folder structure for your S3 bucket before setting up the connector.

**Option A: Unified Path**

```text
s3://your-bucket/conversations/
├── metadata.csv                    # All interaction metadata
├── audio/
│   ├── conv-123456.wav            # Stereo recording
│   ├── conv-123457-agent.wav      # Mono - agent only
│   ├── conv-123457-customer.wav   # Mono - customer only  
│   └── conv-123458.wav            # Stereo recording
├── chat/
│   ├── chat-123459.json           # Chat transcript
│   └── chat-123460.json           # Chat transcript
└── test.csv                       # Required for validation
```

**Option B: Separate Voice and Chat Paths**

```text
s3://your-bucket/
├── voice-interactions/
│   ├── voice_metadata.csv
│   ├── recordings/
│   │   ├── conv-123456.wav            # Stereo
│   │   ├── conv-123457-agent.wav      # Mono agent
│   │   └── conv-123457-customer.wav   # Mono customer
│   └── test.csv
└── chat-interactions/
    ├── chat_metadata.csv
    ├── transcripts/
    │   ├── chat-123459.json
    │   └── chat-123460.json
    └── test.csv
```

## Set Up the Connector

Before you begin, verify that your S3 bucket is ready:

- All audio files are available via HTTPS URLs.
- `.csv` files contain the required fields with correct column headers.
- Mono recordings have separate agent and customer files.
- A `test.csv` file exists in each configured folder.

<Note> File and folder names shouldn't contain any spaces or special characters.</Note>


### Step 1: Create the Connector

1. Navigate to **Quality AI** > **Configure** > **Connectors**.
2. Select **+ Add Connector** > **Amazon S3** > **Connect**.
3. Enter a **Name** for the connector.
4. Select your **AWS Region**.
5. Choose an **Auth Type** and enter your credentials:
   - **Access Keys**: Enter your **Access Key** and **Secret Key**.
   - **IAM Role**: Enter the IAM Role ARN.
6. Set the folder path:
   - **Unified Path**: Enter a single path for both voice and chat (for example, `s3://your-bucket/conversations/`).
   - **Separate Paths**: Enter a **Voice Path** and a **Chat Path**.

### Step 2: Test the Connection

1. Select the **Test** tab in the connector configuration.
2. Select **Test** to validate the configuration. If validation fails, correct the issue and select **Re-Test**.
3. Verify that the following validation checks pass:
   - **Authentication**: Validates your AWS credentials and S3 bucket access.
   - **Filepath Availability & Accessibility**: Verifies that the configured S3 path exists and is available.
   - **File Format Validation**: Verifies that supported file formats are present and readable.
   - **Metadata Validation**: Verifies that required metadata fields are present and valid.

#### Validation Status

The **Test** tab displays validation progress and any errors encountered during testing.

Each validation step can have one of the following statuses:

| Status | Meaning |
|---|---|
| `Pending` | The validation step hasn't tested yet. |
| `Pass` | The validation step succeeded. |
| `Fail` | The validation step failed. The reason for the failure is displayed alongside the failed step. |

<Note>The connector must pass all validation checks before you can proceed with queue mapping and activation.</Note>

### Step 3: Map Queues and Configure the Schedule

1. Navigate to the **Queue** tab.
2. Map each `queueId` from the `.csv` files to a Quality AI Express queue. Values must match exactly.
3. Navigate to the **Schedule** tab.
4. Set the **Interval** (minutes, hours, or days) and **Start Time** (UTC).
The generic connector guide describes a **Start Date** picker as the earliest date from which conversations are eligible to be pulled; conversations recorded before that date are ignored. Confirm whether the AWS S3 Schedule tab uses this same date-based cutoff in addition to, or instead of, the UTC start time.
5. Select **Save** to activate the connector.

After saving, verify the setup is complete:

- The system saves and validates the queue mappings.
- The processing schedule is active.
- The first ingestion job displays in the **Log** tab.
- The system reports no processing errors.

The setup is complete when conversations appear in **Quality AI Express** dashboards and analytics data is available for ingested interactions.

## Troubleshooting

### Authentication

| Problem | Symptom | Resolution |
|---|---|---|
| **Invalid Credentials** | Authentication failed. | Verify the access key, secret key, IAM role ARN, and credential expiration. |
| **Permission Denied** | Access denied to S3 bucket. | Add S3 read permissions to the IAM user or role. Verify the bucket policy and region. |

### File Validation

| Problem | Symptom | Resolution |
|---|---|---|
| **File Access Error** | File or path not found. | Verify the bucket name, region, folder path, and file availability. |
| **Invalid File Format or Metadata** | Validation failed. | Confirm that `test.csv` exists and contains the required structure, column headers, and timestamps. |

### Data Processing

| Problem | Symptom | Resolution |
|---|---|---|
| **Timestamp Errors** | Invalid timestamp format. | Use ISO 8601 format (`YYYY-MM-DDTHH:MM:SSZ`) in UTC. Verify that the end time is after the start time. |

### Performance Considerations

Processing time depends on conversation length, file size, ASR transcription latency for voice interactions, and LLM processing time.

## How Connector Sync Works

The generic connector documentation describes each scheduled sync run as follows:

1. The connector connects to the configured storage location using the saved credentials.
2. It looks for new conversation files added since the previous sync.
3. It retrieves the files referenced by the CSV metadata and sends them for processing.
4. It updates the connector's **Last Sync** value with the current date and time.

Conversations ingested through the connector become available in the relevant Quality AI conversation views, dashboards, and analytics.

### AWS S3 Implementation Details to Confirm

Confirm whether the AWS S3 connector follows the same incremental-file discovery behavior as the generic connector and whether the **Last Sync** value is updated at the same point in the processing workflow.

## Monitoring Connector Logs

Use the connector's **Logs** action to review previous sync runs.

The generic connector documentation specifies that each log entry includes:

- Sync start time and end time.
- Number of conversations pulled in.
- Whether the run succeeded or failed.
