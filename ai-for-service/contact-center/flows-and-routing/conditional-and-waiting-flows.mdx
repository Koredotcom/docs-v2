Contact Center AI lets you customize what customers experience when they wait for an agent, contact you outside business hours, or can't reach an available agent. Use Conditional Flows to control routing behavior for specific scenarios, Waiting Flows to shape the in-queue experience, and the Debug window to troubleshoot flow execution.

| Feature | Description |
|:---------|:-------------|
| [Conditional Flows](#conditional-flows) | Configure voice and chat behavior for out-of-hours, no-agents-available, and click-to-call scenarios. |
| [Waiting Flows](#waiting-flows) | Set up messages, hold audio, callbacks, and voicemail for customers waiting in queue. |
| [Debug and Troubleshoot](#debug-and-troubleshoot) | Review flow execution logs, NLP analysis, and session variables. |

## Conditional Flows

Conditional Flows let you define what happens during three common routing scenarios:

| Scenario | Trigger |
|:----------|:---------|
| Out of Hours | Customer contacts support outside configured Hours of Operation. |
| No Agents Available | No online agents have the skills required for the conversation. |
| In Queue Transfer | Conversation enters a queue before being assigned to an agent. |

Contact Center AI provides default voice and chat flows for Out of Hours and No Agents Available. You can replace or customize these defaults.

<Note>For each channel, you can independently configure fallback messages for No Agent Available and Out-of-Office Hours scenarios . In both cases, the system presents the fallback message to the customer only when no queue-specific configuration exists for the conversation. Queue-specific configurations always take precedence.</Note>

To access Conditional Flows, go to Contact Center AI > Flows & Routing > Conditional Flows.

Plays a voice message to callers who contact support outside business hours.

- Select **Default Out of Operational Hours Voice Flow** to open the flow in the Flow Builder.
![Default Out of Operational Hours Voice Flow](/ai-for-service/contact-center/flows-and-routing/images/default-out-of-hours-voice-flow.gif)

**How the message is selected:**

- The system uses the message from the configured conditional flow.
- If no flow is configured, a non-editable backend default plays.
- Administrators can override the default by creating a conditional flow and attaching it to the experience flow.

### Fallback Messages

If a conversation doesn't match any queue-specific configuration, the system displays a fallback message to the customer. You can configure fallback messages for No Agent Available and Out-of-Office Hours scenarios. 

To configure the fallback message:

1. Select **Fallback Messages** in the upper-right corner.
2. Select **Call Experience**, and turn on the **Enable Fallback Message for No Agent Available** or **Enable Fallback Message for Out-of-Office Hours** toggle.
3. Enter the fallback message and select **Save**.

   ![Fallback Message-Voice](/ai-for-service/contact-center/flows-and-routing/images/fallback-message-call.png)

| Scenario               | Queue-Specific Configuration Exists | Queue-Specific Configuration Doesn't Exist |
| :--------------------- | :---------------------------------- | :----------------------------------------- |
| Out-of-Office Hours    | Queue-specific flow executes.       | Fallback message is displayed.             |
| No Agents Available    | Queue-specific flow executes.       | Fallback message is displayed.             |

### Click-to-Call

Click-to-Call lets website visitors start a voice call directly from the chat widget, providing a seamless escalation path from bot to live agent.

![Click to Call](/ai-for-service/contact-center/flows-and-routing/images/click-to-call-button.png)

Customers can initiate a call:

- Before interacting with the bot.
- During an active bot conversation.
- During a live chat (the chat agent receives a closure notification and moves to After Call Work).

<Note>The Click-to-Call flow appears in Conditional Flows only after it's enabled in [Theme & Design](/ai-for-service/channels/add-web-mobile-client).</Note>

**How flows work:**

- Click-to-Call launches a flow in the Flow Builder.
- A default flow is published automatically. It includes an Agent Transfer node and the message: *"Please wait while we connect you to an agent."*
- Removing the Agent Transfer node triggers a warning before publishing.

**What administrators can add to a Click-to-Call flow:**

- Script nodes
- Message prompts
- Business hours checks
- Queue assignments
- Agent availability checks
- Agent transfers
- End Flow node

**Multiple flows:**

- Administrators can create multiple Click-to-Call flows for different use cases.
- Each flow has a unique **Flow ID**.
- Developers pass the Flow ID in the Web SDK configuration or SDK headers to control which flow triggers.
- SDK headers can pass user metadata (such as page URL) to support conditional logic.

**Developer setup:**

1. Get the **Flow ID** from the Flow Builder.
2. Add the Flow ID and any required headers (user ID, session ID, page name, page URL) to the Web SDK configuration.
3. Deploy SDK updates.

**Web SDK deployment options:**

| Method | How to Update |
|:--------|:---------------|
| NPM Package | Run a standard npm update. |
| Script Tag | Update the version number in the script tag reference. |
| Source Code | Manually apply changes to your modified version. |

<Note>Modifications to SDK source code are made at your own risk. Custom modifications may not receive full support in future SDK updates.</Note>

**End-to-end flow:**

1. The customer clicks the **Call** button in the chat widget.
2. A confirmation pop-up appears. The customer selects **Confirm**.

   - If the customer switches to Click-to-Call during a live chat, the chat agent moves to After Call Work (ACW).

3. The system initiates a voice call to the contact center.
   
   ![Call Connected](/ai-for-service/contact-center/flows-and-routing/images/call-connected.png)
   
   - Context (chat transcript, user ID, session ID, page URL) is passed to the agent.
   - The call routes through the configured Click-to-Call flow.

## Waiting Flows

Waiting Flows let you customize the experience for customers waiting in queue — for both voice and chat channels.

**What you can configure:**

- Routing rules based on agent skills, queues, or skill + queue combinations.
- Routing rules based on agent skills.
- Initial messages when a request enters a queue.
- Hold audio for calls.
- Periodic messages for calls and chats.
- Callback when wait time exceeds a limit.
- Voicemail when wait duration, queue position, or estimated wait time exceeds a threshold.

To access Waiting Flows, go to **Contact Center AI** > **Flows** > **Waiting Flows**.

**Waiting Flows list fields:**

| Field | Description |
|:-------|:-------------|
| Name | Name of the Waiting Experience entry. |
| Queue Rule | Queue rules that determine which conversations use this entry. |
| Skill Rule | Skill rules that determine which conversations use this entry. |
| Description | Brief description of the entry. |
| Edit (icon) | Opens the configuration window for that entry. |

---

### Add a Waiting Experience

1. Go to **Flows & Routing** > **Waiting Flows**.
2. Select **+ New Waiting Experience**.
3. Configure the three tabs: **Configuration**, **Call Experience**, and **Chat Experience**.

---

### Configuration Tab

**Name and Description:**

Enter a **Name** and a brief **Description** for the entry.

**Routing Rules:**

Define which conversations use this Waiting Experience. Conditions can be based on Skill, Queue, or a combination of both.

| Action | How |
|:--------|:-------------|
| Add a queue condition | Select the Queues from the queue dropdown. |
| Add a skill condition | Select the **Skill Group**, then the **Skill**. |
| Add an OR condition | Select the row-level **+ Add** option. |
| Add an AND condition | Hover over a rule row and select **+ Add**. |
| Toggle AND/OR logic | Hover over a rule row and toggle between the options. |
| Remove a condition | Select the **Delete (ⓧ)** icon next to the row or section. |

Supported condition types:

| Condition Type | How to Configure                                              | When It Triggers                                             |
| :------------- | :------------------------------------------------------------ | :----------------------------------------------------------- |
| Skill only     | Add a Skill Group and Skill condition                         | Conversation matches the specified skill                     |
| Queue only     | Add a Queue condition                                         | Conversation enters the specified queue                      |
| Skill + Queue  | Add a Skill condition AND a Queue condition in the same rule  | Conversation matches both the skill and the queue            |

<note>For Skill + Queue combinations, both conditions must be met (AND logic). If the skill matches but the queue does not, or vice versa, the entry is not selected.</note>

**How the system selects a Waiting Experience:**

1. Filters all entries whose routing conditions match the conversation — based on skill, queue, or skill + queue as configured.
2. Sorts by number of routing rules (descending) — more specific entries take priority.
3. If two entries have the same number of rules, the system selects the one created earliest.

The first matching entry in this evaluated order is selected for execution.

**Examples:**

| Conversation        | Matching Entries                                          | Selected Entry | Reason                                      |
| :------------------ | :-------------------------------------------------------- | :------------- | :------------------------------------------ |
| Skill A + Skill B   | Entry 1: Skill A only; Entry 2: Skill A + Skill B        | Entry 2        | More specific (2 rules versus 1)            |
| Skill A + Queue 1   | Entry 1: Skill A only; Entry 2: Skill A + Queue 1        | Entry 2        | More specific (2 rules versus 1)            |
| Queue 1 only        | Entry 1: Skill A only; Entry 2: Queue 1                  | Entry 2        | Entry 1 does not match (skill not present)  |

<Note>Existing skill-only configurations continue to work without modification. Queue-based conditions are additive and do not affect entries that use skill conditions only.</Note>

**Callback Option**

Offer or require a callback when the wait time exceeds a set limit.

1. Turn on the Callback toggle.
2. Set the digit key customers press to request a callback. Choose **Offered** or **Forced**.
3. Edit the callback message. Select **✔** to save or **x** to discard.

**Enable Callback Number Confirmation**

Callback Number Confirmation is an optional feature that lets callers verify or update the phone number they want to receive the callback on before being placed into the callback queue. When enabled, the system launches the Callback Number Confirmation dialog flow after the caller chooses the callback option from the waiting experience. 

The caller can:

- Confirm the caller ID number from which they are calling.
- Enter an alternate callback number, including country code.
- Verify the entered number before final confirmation.
- Complete the callback request using either Dual-Tone Multi-Frequency (DTMF) keypad input or voice input.

Callback Confirmation Flow

The platform installs a default Callback Number Confirmation dialog flow in all existing and created applications. The flow is fully editable and customizable.

The confirmed callback number is stored and used when an agent becomes available. The caller's position in the queue is preserved and the call is disconnected after confirmation.

Default Flow Behavior

1. Callback offer: When the queue wait threshold breaches, callers are offered a callback option. For example: Looks like it might take a while for an agent to become available. To choose the callback option, press 1 at any time during your wait.

2. Number verification: The system reads the caller's phone number digit-by-digit and lets caller to confirm the number or enter a different number for a callback.

3. Alternative number entry: If the caller chooses to provide alternate number for callback, they are prompted to enter a complete phone number, including the country code.

4. Alternative number confirmation: The system reads back the entered number and prompts the caller to confirm or re-enter it.

5. Final confirmation: The system reads the confirmed callback number for the callback request and the caller can disconnect the call.

6. Agent callback: When an agent becomes available, the system initiates the callback request using the confirmed number.

Retry and validation rules

- The system supports both DTMF and Voice Input.

- Callers can retry number entry if validation fails.

- If number capture fails after the configured retry limit, the system follows the configured fallback behavior in the dialog flow.

- Existing callback failure handling behavior remains unchanged.


<Note>Enable this feature only if callers need to confirm or provide an alternate callback number. Otherwise, we recommend leaving it disabled, as it adds additional steps to the callback flow and may impact the caller experience.</Note>


**Voicemail**

Offer or require a voicemail in any of these conditions:

- Call wait duration exceeds `x` minutes.
- Queue position exceeds `x`.
- Estimated wait time exceeds `x` minutes.

To configure:

1. Turn on the Voicemail toggle.
2. Set the digit key that customers press to leave a voicemail. Choose **Offered** or **Forced**.

   | Mode                                  | Behavior                                                                                          |
   | :------------------------------------ | :------------------------------------------------------------------------------------------------ |
   | Offer Voicemail                       | The caller has the option to leave a voicemail after waiting conditions are met.             |
   | Forced Voicemail                      | The caller is automatically directed to voicemail after waiting conditions are met.               |
   | Forced Voicemail with Trigger Immediately | The caller is directed to voicemail as soon as the waiting experience is triggered, with no queue wait required. |

3. Edit the voicemail message. Select **✔** to save or **x** to discard.

   ![Voicemail](/ai-for-service/contact-center/flows-and-routing/images/voicemail-trigger.png)

## Debug and Troubleshoot

The Debug window lets you inspect NLP details, execution logs, and session variables for a chat interaction. Select the **Debug** icon in the upper-right corner of the chat window to open it.

![Debug Logs Icon](/ai-for-service/contact-center/flows-and-routing/images/debug-icon.png)

The Debug window has three tabs:

| Tab | Description |
|:----|:-------------|
| Debug Log | Step-by-step flow execution with timestamps, including Script, Service, and Webhook node logs. |
| NL Analysis | Task loading details and recognition scores for each user utterance. |
| Session Context & Variables | Lists context objects and session variables used during dialog execution. |



### Debug Log

The Debug Log displays the interaction flow in a chat-style format, pairing user inputs with system responses. This makes it easy to trace conversation steps, inspect context at each stage, and identify where issues occur. [Learn more](/ai-for-service/automation/testing/playground#debug-log).

**Events by node type:**

| Node | Initiation Message | Key Events | Outcomes |
|:------|:--------------------|:------------|:----------|
| IVR Menu, IVR Digit Input | IVR Menu/Digit Input node initiated | User input → Transitioning X to Y → Execution completed → Timeout/Retry/Wrong input/Error | — |
| Split | Split node initiated | Transitioning X to Y → Execution completed → Error detected | — |
| Check Agent Availability | Check agent availability node initiated | Transitioning X to Y → Execution completed → Error detected | Agents available/Agents unavailable |
| Check Business Hours | Checking business hours and triggering selected node | User input → Transitioning X to Y → Execution completed | Inside business hours/Outside business hours |
| Message Prompt | Message prompt initiated to the user | Transitioning X to Y → Execution completed | — |
| Automation | Automation node initiated and message triggered | Waiting for user input | — |
| Agent Transfer | Agent transfer node triggered | Transitioning X to Y → Execution completed → Specific dialog executed | Transfer successful/Transfer failure |
| Connect to API | API connection established and node triggered | Transitioning X to Y → Execution completed → Error detected | — |
| Go to Flow, Script Task | Go to flow/Script task initiated | Transitioning X to Y → Execution completed | — |
| Set Queue, Deflection Flow | Set queue/Deflection flow initiated | Transitioning X to Y → Execution completed → Error detected | — |
| End Flow | End flow initiated | Transitioning X to Y → Execution completed | — |
