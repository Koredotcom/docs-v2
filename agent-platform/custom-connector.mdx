The Custom HTTP Connector lets you connect knowledge bases to any REST API service or any data source that exposes HTTP endpoints and ingest its content into the knowledge base for search and retrieval.

## What It Does
It crawls a remote API at configurable intervals, fetches documents from it, and feeds them into the knowledge base ingestion pipeline for chunking, embedding, and indexing. It supports:
- Full sync and delta sync (incremental updates)
- Multiple document objects from one connector
- Permission-aware indexing (ACL crawling)
- Custom scripting to parse non-standard responses

## How It Works
1. Builds a pre-authenticated HTTP client from your attached auth profile. 
2. Paginates your list endpoint and collects item identifiers. 
3. Calls your content endpoint once per item to retrieve the document body. 
4. Chunks, embeds, and indexes each document with metadata and ACL permissions. 

## Configure Custom HTTP Connector

### Step1: Mode

The **Mode** step determines how the connector fetches content from your API. Select the mode that best matches your API structure.

**Most APIs**

Use this mode when your API has separate **list** and **detail** endpoints (for example, `GET /articles` followed by `GET /articles/{id}`).

**How it works**

1. The connector calls the list endpoint to discover new or updated items.
2. It fetches each item individually from the content endpoint.
3. The retrieved content is mapped to document properties, chunked, embedded, and indexed.

**A Single API**

Use this mode when a single paginated endpoint returns the complete content for each item and no additional content request is required.

**How it works**

1. The connector pages through the API response.
2. Each item is mapped directly to a document.
3. The per-item content fetch stage is skipped.

**A Set of IDs**

Use this mode when you have a predefined list of record IDs to index.

**How it works**

1. Specify the IDs in the connector configuration.
2. The connector fetches each record individually.
3. Each retrieved record is indexed.

### Step 2: Connect

Set the API base URL and configure authentication. These settings apply to all requests the connector makes for listing, fetching, or connection testing. 

- **Base URL**: The root URL for your API. All endpoint paths configured in subsequent steps are appended to this URL. Enter the full base URL, including the protocol, for example, `https://jsonplaceholder.typicode.com/`. 
- **Auth profile:** Select the authentication profile the connector should use when calling your API. Defaults to No auth (public API) for APIs that require no authentication. Select a saved auth profile from the dropdown if your API requires authentication. 
- **mTLS client certificate (optional):** Select a client certificate for mutual TLS authentication. Use this if your API requires the connector to present a certificate during the TLS handshake. Defaults to `None` if not required. 
- **Connection test path (optional):** A path appended to the Base URL used solely to verify connectivity. Defaults to `/`. If the root URL returns an error, use a real endpoint such as `/health` or `/v1/items` instead. This is for the connectivity test only; it does not affect any other connector behavior. 

**Testing the Connection**: Click **Test Connection** to verify that the connector can reach your API using the Base URL and the auth profile you have configured. A successful test confirms connectivity but does not validate the listing or fetch endpoints configured in later steps. 

### Step 3: Listing

Define one or more object types to sync from your API. Each object syncs independently and is indexed as a separate searchable document type.

#### Objects

You can configure multiple object types from the same API. Each object appears as a separate tab in the **Listing** step. Click **Add object** to configure an additional object.

For each object, configure the following:

**Object name**

A URL-safe identifier for the object type. It can contain letters, numbers, hyphens (`-`), and underscores (`_`). For example, `articles` or `posts`.

**Listing Mode**

Displays the mode selected in **Step 1: Mode**. This value is read-only. To use a different mode, return to **Step 1** and reconfigure the connector.

**Listing API request**

Configure the API endpoint used to retrieve the list of records.

| Field       | Description                                                                                                                                                       |
| ----------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Method**  | Select the HTTP method.                                                                                                                                           |
| **URL**     | Enter the endpoint path appended to the Base URL configured in **Step 2**, for example, `/items`.                                                                 |
| **Params**  | Add query parameters to include in the request. Click **Add param** to add a key-value pair. Parameters can reference variables using the variable chip selector. |
| **Headers** | Add any request headers required by the listing endpoint.                                                                                                         |

Click **Send** to test the request and inspect the response in the preview panel.

**The object**

Defines how a record from the listing response maps to a searchable document.

- **Items array dot-path**: Specify the dot-path to the array in the API response that contains the individual records. For example, if the response is:

    ```json
    {
    "data": {
        "results": {
        "items": []
        }
    }
    }
    ```
    enter **`data.results.items`**. If the response root is the array itself, leave this field blank.

    You can either click the array in the response preview to populate the path automatically or enter it manually.

- **Attributes**: Define the fields to extract from each record. Click **Add attribute** to map fields from the response.
- **Pagination**: Enable pagination if the listing endpoint returns results across multiple pages. When enabled, values from the response are stored as `ctx` variables and referenced in subsequent requests. For each pagination field, specify:

    - **Field name**
    - **Source path** in the response (for example, `meta.next_cursor`)
    - **Default value** (optional) for the first request

    Additional settings:

    - **Stop paging when**: Controls when pagination stops. The default is **Auto (no more results)**, which stops when no new records are returned.

- **Max pages per sync**: Limits the number of pages processed during a sync. The default is **100000**. Enable **No limit** to continue until all pages have been processed.

**Sync and freshness**: Select how the connector detects changes and performs delta synchronization.

| Option                                      | Description                                                                                                      |
| ------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| **Read everything every run**               | Fetches all records on every sync and compares them locally to detect changes. Scheduled delta sync is disabled. |
| **API filters by changed time**             | Uses a date or time filter to retrieve only records modified since the previous sync.                            |
| **API returns a change cursor**             | Uses a change cursor returned by the API to retrieve only new or updated records.                                |
| **API sorts the newest changes first**      | Retrieves records in descending modification order and stops once older records are reached.                     |
| **List all and compare the modified field** | Fetches the full list each run and compares each record's modified field to determine changes.                   |
| **Compare fetched content hash**            | Computes a content hash for each record and reindexes only records whose content has changed.                    |

**Enable scheduled delta**: Available only when a delta synchronization mode is selected. When enabled, the connector automatically runs delta syncs at the configured interval. Specify the sync frequency using the **Interval** field (in minutes).

### Step 4: APIs

Configure the per-item content request, that is, the API call the connector makes to fetch the full content of each individual record discovered during the **Listing** step. It also defines how the response is mapped to a searchable document. Each object configured in the **Listing** step appears as a tab at the top.

#### Content API

The **Content API** is the endpoint the connector calls once per item to retrieve its full content.

| Field       | Description                                                                                                                                                                                                                                                                                                                                                              |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Method**  | Select the HTTP method.                                                                                                                                                                                                                                                                                                                                                  |
| **URL**     | Enter the endpoint path appended to the Base URL, for example, `/posts/{id}`. Use document field variables in curly braces to inject values from the list response into the URL. For example, `{id}` inserts the `id` attribute of each item. **Insert document field:** Click a variable chip to insert a document field reference into the URL at the cursor position. |
| **Params**  | Add query parameters to include in the content request. Click **Add param** to add a key-value pair or click a variable chip to insert a reference. No query parameters are added by default.                                                                                                                                                                            |
| **Headers** | Add any request headers required by the content endpoint. Click **Send** to execute the request with the test values configured below, then inspect the response in the preview panel.                                                                                                                                                                                   |

**Testing with a sample document** : Set test values for any document field variables used in the URL. Click **Load sample from List** to automatically populate the variables with a real item from the listing response.

#### The Document

Controls how the connector treats each fetched item and which fields it extracts.

**How should we treat each item?**: The following options are available to handle the individual items in response from the **Content API**.

| Option                | Description                                                                                                                                                                                                                                                                                     |
| --------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Document**          | Each list item becomes one document. The content request enriches it, attributes from the list response are read into the request, then fields are picked from the content response. Use this for articles, pages, posts, or any item where the full content lives in a single detail endpoint. |
| **Document + fields** | Each list item becomes one document and also exposes individual fields for selective extraction. Use this when you want both the full document body and specific structured fields, such as title, author, or date indexed, as separate facets.                                                 |
| **Record**            | Each list item is treated as a structured record rather than a content document. Fields are extracted and indexed individually without a document body. Use this for structured data such as product catalogs, user records, or datasets with no long-form content to index.                    |

**Object attributes**: Displays the attributes mapped in the **Listing** step. These are available as variables in the content request URL and are carried through to the final document. To add or change attributes, return to the **Listing** step or click a field in the response preview and select **Add as attribute**.

**Document body**: The dot-path within the content response that holds the main document content, for example, `data.body` or `content.html`. Leave empty to use the entire response as the document body.

**Content type**: Defines how the document body should be interpreted. Defaults to **Auto-detect from response**.

| Option                        | Description                                                                                                                                                   |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Auto-detect from response** | Infers the content type from the response headers and body automatically. Use this when the API sets the correct `Content-Type` header. This is the default.  |
| **Plain text**                | Treats the document body as unformatted plain text. Use this when the content contains no markup or formatting.                                               |
| **Markdown**                  | Treats the document body as Markdown. The connector parses Markdown formatting before indexing.                                                               |
| **HTML**                      | Treats the document body as HTML. The connector strips tags and extracts readable content before indexing.                                                    |
| **JSON**                      | Treats the document body as JSON. Use this when the content field contains a raw JSON string that needs to be parsed rather than indexed as a literal string. |

### Step 5: Fields

Map the attributes you defined on the **List** and **Content** steps to your knowledge base's canonical fields. Mapped fields become filterable metadata. You can adjust these after the first sync.

### Step 6: Review

Review the configurations and save. Click **Start Sync** to start the ingestion process.

## Connector Overview

Once configured, the connector overview displays the sync status, configuration summary, indexed objects, and recent activity for the connector.

**Sync**: Click Sync now to trigger a sync manually.

- Full sync: Fetches all records from the API and re-indexes them regardless of what was previously indexed.
- Delta sync: Fetches only new, changed, or deleted records since the last sync. Available only when a delta mode is configured in the Listing step.
Reconfigure

**Reconfigure**: Return to the setup wizard and modify any connector settings.

**Health**: Shows the result of the most recent sync, including:

- Status (Completed or Failed)
- Sync type (Full or Delta)
- Number of documents processed
- Number of failed documents
- Timestamp

**Configuration**: Displays a summary of the connector setup, including strategy, mode and routes.

**Objects**: Lists each object type configured in the connector along with sync state, document count, last sync time and failures, if any. Click **View documents** to inspect the indexed documents for an object.

**Recent Activity**: Shows the latest sync run status, including the number of processed, failed, and skipped documents.
