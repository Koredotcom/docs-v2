Use this endpoint to retrieve the execution events recorded while agents run. The response groups events by trace and can include LLM calls, tool calls, agent decisions, and failures. Each event provides execution metadata and, depending on the selected `dataMode`, either summary information or the complete sanitized request and response content.

Use `dataMode=summary` when you need operational information such as the event type, model, token usage, duration, cost, or error status without retrieving the event payloads. Use `dataMode=full` when you need the detailed sanitized request and response content associated with the events. To also return the response headers of HTTP tool calls, see [Response headers](#response-headers).

Authenticate with the `x-api-key` header. The key must be bound to the project you are querying and have the `analytics:read` permission.

The endpoint requires a `fromDate` and `toDate` range. The start of the range is inclusive and the end is exclusive. To get a full day, use `fromDate=2026-08-05T00:00:00Z&toDate=2026-08-06T00:00:00Z`. You can further narrow the results by event type, event name, session, trace, event, agent, decision type, channel, environment, or error status. Results are paginated using a cursor; because pagination counts events before grouping them into traces, a page can contain fewer traces than the requested event limit.

To get the next page, pass the `nextCursor` value from the response as `cursor`, and keep every other parameter the same. A cursor is tied to the filters, data mode, and sort order that created it, and changing any of them makes it invalid. Use `limit` to set the number of events per page, from 1 to 10,000. The default is 100.

### Filters

- `fromDate`: **Required.** Inclusive start timestamp for the time range.
- `toDate`: **Required.** Exclusive end timestamp for the time range.
- `eventTypes`: Filter by event category:
  - `llm`: LLM calls
  - `tool`: Tool calls
  - `decision`: Agent decisions
  - `error`: LLM and tool failures
- `eventNames`: Filter by specific event names:
  - `llm.call.completed`
  - `llm.call.failed`
  - `tool.call.completed`
  - `tool.call.failed`
  - `tool.call.skipped`
  - `agent.decision`
- `sessionIds`: Filter events belonging to specific sessions; up to 10,000 session IDs.
- `eventId`: Return only the event with the specified ID. Use this when you need to retrieve a specific event; there is no separate single-event endpoint.
- `traceId`: Return only events belonging to the specified trace.
- `agentName`: Filter events produced by a specific agent. The value is matched exactly.
- `decisionKind`: Filter agent decision events by decision type, such as `routing`, `handoff`, `escalation`, or `completion`.
- `channel`: Filter by the exact channel name recorded for the event. Pass a single value. Unlike the Sessions endpoint, this filter does not support channel aliases, so use `web_chat` rather than `web`.
- `environment`: Filter by environment: `dev`, `staging`, `production`, or `working-copy`. Pass a single value.
- `hasError`: Set to `true` to return only events with errors, `false` to return only events without errors, or omit the parameter to return both.

The `eventTypes` filter accepts up to four categories. The `eventNames` filter accepts up to 20 names. Unsupported event names are ignored rather than rejected and are reported in `meta.unsupportedEventNamesRequested`.

### Response headers

Set `includeResponseHeaders` to `true` to return the response headers of HTTP tool calls. The headers appear under `eventData.payloadData.responseHeaders`. The default is `false`.

- The parameter requires `dataMode=full`.
- Header names are lowercase. Repeated headers are joined with a comma and a space.
- Credential headers, such as `authorization`, `set-cookie`, and `x-api-key`, keep their name. Their value is `[REDACTED]`.
- When the call was retried, the headers come from the final attempt.
- `responseHeaders` is an empty object when the event has no headers. This happens when the tool is not an HTTP tool, no response arrived, or the event was recorded before header capture existed.
- `responseHeadersTruncated` is `true` when headers were dropped to keep the stored names and values within 16 KB.

The parameter accepts `true`, `false`, `1`, or `0`. Other values and invalid combinations return a `400` error:

| Error code | Cause |
|:-----------|:------|
| `INVALID_PARAM_COMBINATION` | `includeResponseHeaders=true` with `dataMode=summary`, or without `dataMode`. |
| `INVALID_INCLUDE_RESPONSE_HEADERS` | A value other than `true`, `false`, `1`, or `0`. |

### Workflow runs

When a tool call starts a workflow, the event includes the run in `eventData.workflowRun`. This applies to tool events where `toolType` is `workflow`, including `tool.call.failed` events. The object lists the steps in the order they ran. It doesn't include step inputs or outputs.

| Field | Description |
|:------|:------------|
| `executionId` | The ID of the run. |
| `workflowId` | The ID of the workflow. |
| `workflowName` | The name of the workflow. |
| `status` | The status of the run, such as `running`, `completed`, or `failed`. |
| `startedAt`, `completedAt` | The start and end timestamps of the run. |
| `durationMs` | The duration of the run in milliseconds. |
| `stepAvailability` | `complete`, or `partial` when some steps aren't available yet. The `steps` list then holds only the available steps. |
| `stepsTruncated` | `true` when the run has more than 200 steps. Only the first 200 are listed. |
| `steps` | The top-level steps of the run. Steps that a loop runs for each item aren't listed. |

Each item in `steps` has the following fields:

| Field | Description |
|:------|:------------|
| `name` | The name of the step, as written in the workflow. |
| `stepId` | The ID of the step. |
| `nodeType` | The kind of step, such as `http`, `function`, or `email`. |
| `status` | `running`, `completed`, `failed`, `rejected`, `skipped`, `cancelled`, or a `waiting_` status such as `waiting_approval`. |
| `startedAt`, `completedAt` | The start and end timestamps of the step. |
| `durationMs` | The duration of the step in milliseconds. |
| `error` | The `code` and `message` of a failed step. The message has personal data removed under the project's PII settings. |

`workflowRun` is absent when the run could not be loaded. The events are still complete. In that case, `meta.warnings` explains why.

### Warnings

`meta.warnings` is present only when part of the page could not be served in full. Each warning has a `code` and a `message`. The only code is `WORKFLOW_STEPS_UNAVAILABLE`. It means some workflow tool calls are returned without `workflowRun`. The events themselves are complete.

Use `GET` when:

- You are retrieving trace data without requiring encrypted request parameters.
- You want to inspect or troubleshoot a specific event using `eventId`.
- You want to investigate a particular trace using `traceId`.
- You are analyzing events for one or more sessions using `sessionIds`.
- You need to query and page through trace data using standard URL parameters.

<Caution>Do not use GET when the request parameters themselves must be encrypted. GET query strings are never encrypted.</Caution>

To send the query parameters in a request body instead of the URL, use [List trace events using JWE payload](/agent-platform/api-reference/analytics-list-traces-with-encrypted-payload).
