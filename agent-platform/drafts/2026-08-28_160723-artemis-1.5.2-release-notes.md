<Update label="August 27, 2026" description="v1.5.2, Patch release">

<p className="rn-title">Voice Experience</p>

<p className="rn-subtitle">Embed inbound SIP header values directly in the call transfer destination</p>

A voice transfer destination can now carry a `{{sip.<header>}}` placeholder — for example `sip:421003@172.0.41.7:5060;user=phone?User-to-User={{sip.user-to-user}}` — which is resolved server-side from the inbound call's SIP headers at transfer time. This covers receiving systems (such as Avaya) that require a per-call value inside the INVITE's destination URI itself, rather than as a header carried alongside the REFER. The placeholder is required-if-present: if the inbound value is missing, the transfer fails closed instead of dialing a half-composed destination.
<br />*No public how-to article exists yet for this mechanism — flagged for the docs team; see the audit report for the relevant existing pages to extend.*

<p className="rn-subtitle">No more dead air before an agent transfer connects</p>

Voice call transfers using `call_transfer` with `LiveTransferAgent` no longer block the agent's other responses until the transfer completes or times out. Any speech the agent already queued now plays out before the blocking dial begins, so callers hear the agent instead of silence while a transfer is in progress.
<br />[Learn more →](/agent-platform/escalate)

<p className="rn-title">Agent Builder Experience</p>

<p className="rn-subtitle">Base64 attachment uploads and regenerable delivery URLs</p>

Alongside the existing `multipart/form-data` upload path, the platform now accepts a strict `application/json` attachment upload using `filename`, `mimeType`, and `contentBase64`. Every successful upload also returns a short-lived delivery URL descriptor; if that URL is not yet available or has expired, a new one can be requested on demand from a dedicated endpoint without re-uploading the file.
<br />*No public API reference article exists yet for attachment upload/delivery — flagged for the docs team.*

<p className="rn-subtitle">Workflow Agent node accepts attachment IDs</p>

The Agent node's canvas attachments field now accepts attachment IDs directly, in addition to http(s) URLs, so a workflow can hand an already-uploaded attachment to an agent node without re-hosting it as a URL first.
