Configure guardrail providers and policies for content safety and compliance.

Navigation: Settings > AI Configuration > Guardrails

Required role: Owner or Admin

Workspace guardrails define organization-wide content safety policies that apply across all agents, catching harmful, inappropriate, or off-topic content before it reaches end users. The Guardrails page is organized into two sections: **Guardrail Providers** and **Guardrail Policies**.

**How Guardrails Work**

Guardrails evaluate agent inputs and outputs against configurable safety categories and take a configured action — block, warn, or log — when content violates a policy. Guardrails can also evaluate inbound user messages to prevent prompt injection and jailbreak attempts.

**Guardrail Providers**

Guardrail providers are the evaluation services that assess content against your safety policies. You must configure at least one provider before creating policies.

The Guardrail Providers section shows the count of configured providers and a refresh control. Click Add Provider to configure a new one.

**Adding a Provider**

1. Go to Settings > AI Configuration > Guardrails.

2. Click Add Provider.

3. In the Add Guardrail Provider dialog, configure the provider using the Form or YAML tab.

4. Click Add Provider to save.

**Form tab fields**:

| Property          | Description                                                                 |
|-------------------|-----------------------------------------------------------------------------|
| Name              | A unique internal identifier for the provider (for example, *OpenAI Moderation*). |
| Display Name      | A human-readable label for the provider (for example, *Content Safety (OpenAI)*). |
| Adapter Type      | The type of guardrail adapter. Select from available adapter types (for example, *OpenAI Moderation*). |
| Hosting           | The hosting model for the provider. Default: **Cloud API**.                 |
| Endpoint URL      | The provider’s API endpoint URL (for example, *https://api.provider.com/v1/moderation*). |
| Model             | The model used by the provider for evaluation (for example, *text-moderation-latest*). |
| Authentication    | Toggle on to enable authentication. Note: Raw API keys aren't accepted. Use an **Auth Profile** for providers requiring credentials. |
| Default Category  | The default content category this provider evaluates (for example, *content_safety*). |
| Default Threshold | The default sensitivity threshold (**0.0 to 1.0**). Default: **0.7**. Lower values flag more content; higher values flag only high-confidence violations. |

**Retry Configuration**:

| Property        | Description                                                                 |
|-----------------|-----------------------------------------------------------------------------|
| Max Retries     | Number of retry attempts if the provider call fails. Default: **3**.        |
| Backoff Strategy| Backoff interval in milliseconds between retries. Default: **1000**.        |
| Enabled         | Toggle on to enable this provider for guardrail evaluation.                 |

**Provider Health Monitoring**

The Guardrail Providers section shows the health status of each configured provider. The platform periodically checks provider health. If a provider becomes unhealthy, its circuit breaker activates. After repeated failures, the circuit breaker opens and stops sending requests. After the reset timeout, the circuit breaker allows a test request through.

When a guardrail provider's circuit breaker is open, the platform follows the provider's configured fail mode:

- Fail-open -- Content is delivered without guardrail evaluation. Violations may go undetected.

- Fail-closed -- Content is blocked until the provider recovers. This is safer but may interrupt service.

**Guardrail Policies**

Guardrail policies define the rules applied to agent inputs and outputs for a specific project. The Guardrail Policies section includes a Project dropdown to select the project you want to configure policies for.

**Content Safety Categories**

| Category           | Description                                                                 |
|--------------------|-----------------------------------------------------------------------------|
| Hate speech        | Content that promotes hatred or violence against groups based on protected characteristics |
| Sexual content     | Sexually explicit material inappropriate for the agent’s use case           |
| Violence           | Graphic descriptions of violence or instructions for causing harm           |
| Self-harm          | Content that encourages or instructs self-harm                              |
| PII detection      | Personally identifiable information (names, emails, phone numbers, SSNs) in outputs |
| Profanity          | Offensive language and slurs                                                |
| Prompt injection   | Attempts to override agent instructions through crafted inputs              |
| Off-topic          | Content outside the agent’s intended domain                                 |
| Hallucination risk | Responses that may contain fabricated information (requires knowledge base context) |

Each category has a configurable threshold (0.0 to 1.0). Lower thresholds flag more content; higher thresholds only flag high-confidence violations.

**Creating a Policy**

1. In the Guardrail Policies section, select the target project from the Project dropdown.

2. Click Create policy.

3. Give the policy a name and description.

4. Select which categories to evaluate.

5. For each category, configure:

   - Threshold -- Sensitivity level (0.0 = flag everything, 1.0 = flag only high-confidence violations).

   - Action -- What happens when content is flagged:

     * Block -- Prevent the response from reaching the end user. A fallback message is shown instead.

     * Warn -- Deliver the response but add a warning annotation visible to operators.

     * Log -- Record the violation for analytics without affecting the response.

6. Set whether the policy evaluates inbound messages, outbound responses, or both.

7. Click Save.

**Linking Policies to Projects**

Workspace guardrail policies are available to all projects, but each project chooses which policies to activate:

1. Open the project in Studio.

2. Go to Project settings > Guardrails.

3. Toggle on the workspace guardrail policies you want to enforce for this project.

4. Optionally adjust thresholds at the project level. Project settings override workspace defaults when more restrictive.

When both workspace and project guardrails exist:

- Workspace policies evaluate first. If a workspace guardrail blocks content, the project guardrail isn't consulted.

- Project policies add specificity. Use them for domain-specific rules (for example, blocking financial advice in a customer support agent).

- The most restrictive action wins. If the workspace policy says "warn" but the project policy says "block" for the same category, the content is blocked.
