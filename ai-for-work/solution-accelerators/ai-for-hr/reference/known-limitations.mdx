AI for HR draws clear boundaries around what each agent does. Read these limits before you scope your rollout, so your communication to employees matches what the assistant delivers.

The limits fall into three groups: scope limits inside each domain, coverage limits across the application, and behavior that looks like a limit but follows the design.

## Scope limits by agent

Each specialist owns one domain and refuses work outside it. The supervisor routes those requests to the agent that owns them.

| Agent | Limit |
|-------|-------|
| **HR_Supervisor** | Routes only. It performs no HR work and runs no transaction tool. |
| **Time Off Assistant** | Submits nothing until the employee confirms, and never bypasses a balance, eligibility, holiday, or weekend validation. |
| **Benefit Management** | Covers coverage, enrollment, eligibility, and dependents only. |
| **Compensation** | Serves the logged-in employee only. It cannot modify payroll, issue refunds, or resolve disputes. |
| **Profile Management** | Updates selected fields only, and requires supporting documentation for sensitive fields. |
| **Case Management** | Cannot approve HR requests, and changes a case only by running a tool. |
| **Offboarding Management** | Handles voluntary resignation only, and never assumes intent. |
| **Timesheet Management** | View-only, and limited to the employee and their direct reports. |

## Coverage limits

Four limits apply across the whole application. Plan your rollout and your knowledge content around them.

| Limit | What it means |
|-------|---------------|
| **Region scoping** | Case Management infers the region from the message and passes either India or the US downstream. Employees in other locations get answers only from content indexed for those two regions. |
| **Knowledge boundary** | Agents answer policy questions only from content indexed in Search AI. When nothing matches, the agent offers to raise a case rather than answering from general knowledge. |
| **Systems of record** | The shipped tools call Workday and ServiceNow. Any other system needs its own HTTP tools on Agent Platform. |
| **Identity configuration** | HTTP tools resolve the employee identity from config variables, such as `{{config.EMPLOYEE_ID}}`. Confirm these values for every environment before testing. |

<Warning>The `benefits_for_employees` tool ships with a fixed `employee_id` in its request body. Replace it with a config variable, or every employee sees the same available plans.</Warning>

## Behavior that looks like a limit

Some responses surprise employees at first, even though the design intends them. Share this list with your pilot group.

| What employees see | Why it happens |
|--------------------|----------------|
| The assistant asks for confirmation before every change. | Every write path requires explicit in-chat confirmation. |
| Control returns to the previous agent after a topic change. | Every HANDOFF block uses `RETURN: true` and `ON_RETURN: continue`. |
| A value differs from what the employee expected. | Agents surface values verbatim from the system of record. |
| The assistant offers a case instead of an answer. | The knowledge search found no matching content. |
| The assistant asks for a missing date or boundary. | Agents surface missing information rather than assuming it. |
